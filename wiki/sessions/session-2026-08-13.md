# Session 2026-08-13

Longest single session of the project so far — full 8-series Figma build, a new reusable-library architecture pattern, a real production data cleanup, and the first-ever live end-to-end deploy of an agent through the real app onto real Meta infrastructure.

## 8-series Figma build (Agents module)
Continuation of the "no whitewashing" discipline set earlier this week on the Dashboard screen (see 2026-08-12 memory). Built in stages, each verified against real `get_design_context` content, not screenshots:

1. **Agents List "About" column + Empty State** — real backend field (`about_label`, additive `V42`), not a reused `systemPrompt`. Caught and fixed a real bug in the same pass: the "Add a label" and Settings-tab saves both hit `PUT /agents/:id`, which replaces the whole payload — a partial body would have silently nulled tone/language/behaviorRules/handoff.
2. **Agents home re-audit** (founder: "its not changed") — breadcrumb, single grouped Filters panel (DESIGN.md §6, never loose dropdowns), Enabled toggle backed by the real deploy/pause endpoints, "Continue setup" for drafts.
3. **3 Library pages rebuilt as card grids** (Skills/Connectors/Business Persona) — real data only. "Used by N agents" is a genuine join for Skills; Connectors/Persona show "Live on {agent/number}" where no such relationship exists rather than fake a count.
4. **7-step Create-Agent wizard rebuilt** (Basics/Business Persona/Knowledge Base/Skills/Connectors/Evals/Test&Deploy) from the old 6-step version, each step backed by real existing endpoints. Iris rail wired to the real session API but flagged as unable to write into wizard fields yet (no tool exists for that).

Two background agents collided mid-build (same files, same task) — one detected the collision and self-aborted cleanly, deleting its own orphan file rather than race the other writer. See [[../bugs-violations/concurrent-agent-collision-2026-08-13|writeup]].

A UX-gate-style review caught real DESIGN.md token violations in the first Empty State pass (arbitrary caption sizing, off-4px-grid height, raw RGBA shadow) — all three fixed to reuse existing tokens (`shadow-surface-lifted`, the file's own caption class, `h-4`).

## Reusable-library architecture pattern extended to Connectors
Founder's framing: *"Meta just exposes the APIs, we build the product"* — our DB should be the source of truth for reusable definitions (Agents/Skills/Connectors), Meta is the execution/transport layer underneath. See [[../decisions/reusable-library-over-meta-execution-2026-08-13|full decision]]. Built in two passes:
1. A live-state **mirror** (`agent_connector`, `V45`) — upsert-on-read cache of Meta's per-phone connector state, serves last-synced rows with `cached: true` if Meta is unreachable. Secrets never mirrored.
2. A real **library layer** (`connector` + `connector_deployment`, `V46`) sitting above the mirror — a connector definition that exists independent of any agent, deployable to N agents, with a genuine `COUNT(*)` for "used by N agents" instead of the mirror's name/base_url heuristic.

Flagged, not built: `Agent` itself conflates "definition" and "deployed instance" the same way Connectors used to — same review candidate, deliberately untouched.

Hit two real bugs live, both caught and fixed on the spot: `messages` deleted before `conversations` (RESTRICT FK, wrong order) and a collation mismatch between `agent.phone_number_id` (`utf8mb4_unicode_ci`) and `business_profile.phone_number_id` (`utf8mb4_0900_ai_ci`), fixed with an explicit `COLLATE`. Both failures rolled back cleanly (Flyway wraps each migration in a transaction) — no data was ever at risk.
- `V48` — deleted 4 leftover draft test agents by explicit id, same cascade pattern, succeeded clean on the first try since it reused the lessons from `V47`.
- Disk cleanup: `/tmp` on the server cleared (~530MB of already-applied deploy artifacts), `/var/www/metaagent.bak*` pruned from 46 directories to the 3 most recent.
- Dead frontend code removed: `SkillsTable.tsx`/`PersonaTable.tsx` (329 lines, only their exported types were still used — moved to two small `*Types.ts` files first).
- Orphaned backend endpoint removed on founder's explicit call: `generate-defaults` (service, DTOs, controller mapping, rate-limit rule, config) — dead since the new wizard has no "Generate with AI" button.

**Important gap surfaced by this cleanup, not fixed yet:** `V47` was a raw migration — it only cleaned our local DB, it never told Meta anything. Every one of those 6 "deleted" agents was still fully live on Meta's side. See [[../bugs-violations/hard-delete-migration-never-touches-meta-2026-08-13|writeup]].

## Real bug found + fixed: agent delete cascade was missing 3 tables
`AgentService.deleteAgent`'s local cascade was written before the connector-mirror (`V45`) and connector-library (`V46`) features existed, and was never updated when they landed. A real delete against any agent with connector history threw a live `SQLIntegrityConstraintViolationException` on `agent_connector`'s FK. Fixed by adding `deleteAllByAgentId` to `AgentConnectorRepository`, `ConnectorDeploymentRepository`, and `AgentSkillAttachmentRepository`, wired into the cascade in FK-safe order. Full writeup: [[../bugs-violations/agent-delete-cascade-missing-tables-2026-08-13|here]].

## First-ever live end-to-end agent deploy
Founder asked to deploy a full agent through the actual product — no Playwright/Selenium available in this environment, so it was driven via the same HTTP endpoints the UI calls, in the same order, using real founder-provided credentials (`demo@karix.online`) against the real WABA `494227720434920`.

This is where the delete-cascade fix above got its first real live test — twice, against real Meta, both `metaFullyCleaned: true` (one deleted 11 real skills, the other 23 skills + a real connector). It's also where the migration-doesn't-touch-Meta gap above was discovered: every "deleted" demo agent's phone number still showed connected on Meta, and got auto-rediscovered by the reconciliation service mid-task.

Hit a real, external, non-code blocker: two phone numbers showed Meta's own **"Get started"** state (WhatsApp Business Agent never onboarded for that number at all) — no API call can substitute for that first-touch step; a human has to click it in Meta Business Manager. Founder did so mid-session; the deploy then went straight through:

1. **Basics** — created `Karix Support Agent`, bound to `+91 91520 04283`.
2. **Business Persona** — deployed real business info (returns/delivery/payment/hours) to Meta.
3. **Knowledge Base** — added a FAQ, synced (`metaSynced: true`).
4. **Skills** — hit a real Meta validation rule live (skill titles must be lowercase-hyphenated slugs, no spaces/capitals) — a genuine client-side-validation gap worth adding. Fixed the one call and synced.
5. **Test & Deploy** — deployed (`status: active`, real `metaAgentId`), sent a live test message, got a correct real AI response back quoting the exact FAQ answer just loaded.

First time this project has proven a fully real, non-mocked, agent-creation-to-live-response loop end to end.

## Real client use case: IndiaMART Buyer Discovery Agent
Same session, immediately after: a real client scoping email (IndiaMART, via Ashutosh) asking whether the platform can replicate their buyer-discovery journey for WhatsApp text — intent/entity extraction, clarification on ambiguous products, IndiaMART Supplier Search/Pricing API calls, ranked conversational results, session context for follow-ups. Built as a second real deployed agent (4 skills, 1 UI skill, 3 Connector Library definitions) on the same demo WABA, phone `+91 91520 04195`.

Caught myself mid-build fabricating a plausible-but-unverified IndiaMART API contract (base URL + field names guessed from general knowledge of their seller-side CRM API, presented as if it were the real buyer-side Supplier Search endpoint) — corrected immediately to an honest `TBD-confirm-with-indiamart.example` placeholder before it could be mistaken for verified. The Google Sheets connector, by contrast, was built for real since its public API contract is genuinely stable, documented knowledge, not a guess.

All 3 sample journeys from the client's own email verified live: unambiguous query (honest "no results" since no real connector is deployed — proves the never-fabricate skill holds under a real no-data condition), ambiguous "pipes" query (clarification near-verbatim matching the client's own PVC/GI/HDPE example), and a 3-turn follow-up ("show me cheaper suppliers" correctly resolved against "PVC pipes, Mumbai" from two turns earlier with nothing repeated) — proving conversation-context/session behavior works exactly as the client's email asked, live, not just in skill prose. ## API Calls log gets real filters; Iris chat list's timezone bug found and fixed
Founder asked whether connector errors show up in the UI (in service of scoping the Events feature, which will have the same "did this silently fail" risk) — answer: logged in the DB, not really findable in the product, because Reports → API Calls had no filter at all and the most-recent-200-row window gets flooded by `GlobalSyncScheduler`'s routine reconciliation polling within minutes. Added real filters: `ApiCallLogFilter` + JPA `Specification` (method, path-contains, outcome ALL/SUCCESS/ERROR, from/to), exposed on `GET /reports/api-calls`; frontend gets preset chips for the app's own vocabulary (Connectors/Skills/Files/Websites/FAQ/Settings/Allowlist/Events/Eval/Persona) plus free-text path search, method/outcome dropdowns, and a date-time range.

Building the date-time range surfaced a second, independent bug while fixing the first: `TemplateIrisAllChatsPage.tsx` ("All chats") was using raw `new Date(iso)`/browser-locale formatting for message timestamps and Today/Yesterday bucketing — the exact class of bug already fixed everywhere else on 2026-08-07, but this file was never migrated onto the shared `dateFormat.ts` fix. Founder's report ("the entire product's timing isn't Indian time") was correct for this one screen. Fixed by exporting `parseAsUtc` and adding `istStartOfDayMs`/`istInputToUtcNaiveIso` to the shared util, then wiring the chat list onto it. Full writeup, including the near-miss of almost shipping a second copy of the same bug inside the new datetime filter inputs themselves: [[../bugs-violations/api-calls-log-no-filter-and-iris-chat-list-wrong-timezone-2026-08-13|here]].

Also decided, ahead of building it: Events (trigger → outbound action) belongs as an Agent Detail tab, not a new nav section — it's per-agent conversation-flow config like Skills/Persona/Settings, not a cross-agent reusable asset. The reusable part (the CRM/webhook target itself) should point at a Connector Library definition, reusing the same definition/deployment split Skills and Connectors already have — not started yet, this was scoping only.

## Critical fix: BizAI-active messages were never reaching Conversations
Founder texted "Hi" to the live IndiaMART agent (`+91 91520 04195`, after first mistakenly texting an old paused test number, `+91 91520 04492` — sorted out via a live investigation over SSH + the app's own API, no direct DB access) and it never showed in the Conversations tab. Traced through real `app.log` on the production server: the webhook arrived, was correctly attributed to the right agent, but every time logged `BizAI active on webhook — observability only, no action taken` and persisted nothing. Root cause: `InboundMessageParser` only ever read the top-level `value.messages` webhook path; per `docs/meta-api/webhook-standby-handoff.md`, when Meta's own AI is actively responding — the normal case for every live deployed agent, not an edge case — the real customer message is nested under `value.standby.messages` instead, a path `HandoffClassifier` already checked for its BIZAI_ACTIVE signal but nothing ever extracted the message from. This meant no live, working agent's customer messages were ever visible in the product's own Inbox. Fixed (parser now checks both paths), tested, and deployed to production: jar built, byte-verified over the bastion double-hop, old jar backed up, service restarted, clean startup confirmed in `app.log`, verified reachable via a real post-deploy login. BizAI's own reply text (a separate shape, `value.standby.message_echoes[]`) is still not captured — flagged as an explicit follow-up, not silently dropped. Full writeup: [[../bugs-violations/bizai-active-messages-never-persisted-2026-08-13|here]].

## Eight critical items from internal team feedback
Founder relayed 8 items framed as "critical... else it will never fly," directly after the BizAI-messages fix above. Verified each against real code before building (several turned out already solved, one — item 3/6 — turned out to be genuine data loss):
1. Log every outbound Meta call, even background-triggered — already true (`GlobalSyncScheduler`'s own docs confirm this fixed 2026-08-03), no code needed.
2. API Calls filter gains phone number + agent id, both new `api_call_log` columns (`V51`) resolved at write time.
3/6. **Real gap, fixed**: `WebhookController` silently dropped (never persisted) any payload it couldn't attribute to a known agent or that failed signature verification — `webhook_raw.account_id` was `NOT NULL` so there was no way to store them. `V50` relaxes that, adds `phone_number_id`; every payload is now persisted (status `FAILED` + reason for the unattributable/sig-fail cases); Inbox's Webhooks panel gets real filters (phone/agent/status/date), visible across accounts for unattributed rows (nobody owns them, hiding them recreates the same problem).
4. Post-login redirect to Webhooks — a `postLogin` router-state flag set only by a real login, read by `RootRedirect`, deliberately not a hardcoded change to the module's normal home route (would've undone the 2026-08-04 module-resolution fix).
5. Conversations list now shows which of the account's several business numbers a conversation came in on — resolved via the owning agent (`Conversation` has no phone field of its own), batched per page.
7. Agents list: "Add a label" replaces an auto-retry that often never resolved a real name; About column now sourced from the real deployed Business Persona instead of a disconnected manual field; Health column (redundant with the Enabled toggle) replaced with Agent ID (needed for the new filters above).
8. Draft/publish extended honestly, not uniformly: Skills already had a real draft-vs-publish split (Library save never touches Meta, legacy agent-scoped save does) — just relabeled to say which is which. Connectors relabeled "Publish" since every save is already an immediate Meta write (no Meta-side draft-connector concept exists), with a note pointing at the pre-existing connector-creation bug. Evals/Events are one-shot action triggers with no persisted editable state at all — confirmed by reading both components — so no Draft/Publish badge was forced onto them; that would be decorative, not a real fix.

Verified: `mvn -q -o compile` clean (backend, twice), `npm run build` clean (frontend — the full `tsc -b && vite build` caught one dead import `tsc --noEmit` alone had missed). Deployed to production with full backup discipline (fresh `mysqldump`, old jar + frontend dist both backed up before swap) — hit two real issues live, both fixed before calling it done: `V50` failed its first attempt (MySQL rejected a nullable FK column that had silently lost its `UNSIGNED` attribute), and the new `ApiCallLog.agentId` field was missing the `ToStringSerializer` annotation every other TSID field in this codebase carries, silently corrupting large ids past `Number.MAX_SAFE_INTEGER` — caught only by cross-checking the same agent's id between two endpoints. Full writeup: [[../decisions/eight-critical-internal-feedback-items-2026-08-13|here]], deploy detail: [[../deployment/eight-items-deploy-2026-08-13|here]].

## Connectors, UI skills, and a real "silent agent" incident (same day, later)
Founder asked to prove out Connectors/Tools, Custom Prompts, Business API invocation, and Interactive Elements (Carousel/CTA/List) end-to-end on the IndiaMART agent. Found and fixed, in order: 3 real Meta `agent_connectors` validation bugs (`auth_config` nesting, `auth_config` required even for `NONE`, connector `name` must be a plain identifier — see [[../bugs-violations/connector-creation-never-succeeds-2026-08-13|full writeup]]); a redirect + `base_url`/`path` composition bug on the Supplier Search connector's Google Sheets data source, fixed by moving to an Apps Script Web App (same pattern as the already-working Pricing connector) plus response caching for latency; built and live-verified real Carousel (`carousel_quick_reply`) and Call CTA (`cta_url`) UI skills (see [[../decisions/interactive-elements-audit-2026-08-13|audit + build writeup]]).

While demoing, the agent appeared to go silent to a real WhatsApp customer — zero outbound messages in our DB despite `agent_test` succeeding. Founder sent real messages from their own phone and pasted the actual transcript: BizAI was genuinely replying (including a correct handoff trigger) — none of it was ever persisted. Root cause: `OutboundEchoParser` (built earlier the same day) read the echo's `to`/`type`/`text.body` fields from the wrong JSON nesting level — a never-verified guess. Fixed with the real, confirmed shape, plus a defensive flat-shape fallback since Meta's shapes have now proven unreliable to assume twice — founder's explicit instruction after this incident: log everything, don't assume any related webhook shape (e.g. human handoff's own) is correct until checked against real captured traffic. Full writeup: [[../bugs-violations/echo-parser-wrong-nesting-2026-08-13|here]]; `docs/meta-api/webhook-standby-handoff.md` updated with the verified real shape.
