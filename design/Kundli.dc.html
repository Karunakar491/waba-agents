What this API exposed

1 — The Required column is almost useless here, and my earlier artboards hid that

Meta records required-ness only as body.required, a list of top-level field names. The only top-level field in this API is detail. So day, month, year, lat and lon — which the API genuinely rejects the call without — cannot be marked required at all. Every one shows a dash.

Which answers the question directly: the description is not documentation, it is the contract. It is the only place a constraint can live, so it carries the range, the unit, the format and the word “required” in words. Meta has no min, no max, no pattern either.

2 — Two fields need the agent to convert, not to relay

A person says “born in Bankura”. This API wants lat: 23.23, lon: 87.07 in decimal degrees, and it will not geocode place for you. So those two descriptions have to say decimal degrees, not a place name, with an example — or the agent will send the string and the call fails. hour is the same trap: “12 midnight” must become 0.

3 — A failure arrives as HTTP 200

{"status":"failed","reason":"lat and lon are required"} comes back 200 OK. Nothing in Meta's tool model can express “200 but check a field”, so the action’s description — not a field’s — has to tell the agent to read status before trusting the body, and to relay reason. Without that the agent reports success on a failed call.

A green 200 OK in the response pane would say the same wrong thing, so the pane has to show the body and not just the status line.

The action’s own description — Docs

Generates a full Kundli report from a person’s birth date, exact time and birth place. Ask for all three before calling — the report is wrong, not merely incomplete, if the time is guessed. The reply is a 200 even when it fails: check status, and if it is failed, tell the person what reason says instead of reporting a result.

Two sentences of behaviour and one of failure handling. This is the text Meta hands the model verbatim to decide when to call the action, so it is the highest-consequence copy on the screen — which is why the Description column is always visible here rather than hidden behind an info icon, as it is in Postman.
