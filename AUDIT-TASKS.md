**F1. [CRITICAL] No embedded WABA signup — manual WABA-ID entry is the only onboarding path.**
`WabasPage.tsx` requires the user to already know and type their WABA ID, then validate it. There is no Meta Embedded Signup (FB.login/Graph OAuth) flow anywhere in the codebase (`grep` for embedded signup / FB.login / coexistence returns nothing). This is the single biggest gap against the PM thesis ("the user wants to talk to customers, not learn APIs") — a non-technical business owner cannot get a WABA ID without going through Meta Business Manager themselves first, which is exactly the API-wrapper experience this product claims to abstract away. **Violates:** the product's own stated wedge ("gap is a product that feels like a conversation partner... not a raw API wrapper") and CLAUDE.md's "non-technical" user framing. **PM READ:** THESIS — onboarding friction kills SMB activation faster than any other single factor. BET — embedded signup would cut time-to-first-connected-number from "requires Meta Business Manager knowledge" to minutes. RISK — Meta's embedded signup requires app review/approval and Tech Provider status; may be a real technical/compliance blocker, not just a build gap. RECOMMENDATION: confirm with EM/founder whether Meta Tech Provider embedded signup is available to us; if not yet, this is a roadmap P0, not a bug — but the current state should not be mistaken for "done."

**F2. [HIGH] No account-level onboarding gate — a brand-new account lands on an empty Dashboard with no forced setup.**
`ProtectedRoute.tsx` only checks auth + module entitlements, not "has this account created a WABA/agent yet." A first-time login goes straight to `/dashboard` or `/select` with zero guidance. Per persona-pm's "what they abandon" list — "anything that requires reading documentation" — an empty dashboard with no next-step CTA is a silent abandonment risk. **Violates:** no explicit CLAUDE.md rule, but directly contradicts the PM persona's core thesis (smart defaults over configuration, anticipatory not reactive). **RECOMMENDATION:** first-login state should redirect to a single guided "connect your first WABA" step, not a routed dashboard full of empty-state cards.

**F3. [HIGH] Template Studio, Iris, and all Library pages (Skills/Files/Connectors/Persona) are reachable with zero WABAs/agents and rely on in-page empty states rather than sequencing.**
Confirmed: `/templates`, `/templates/iris`, `/library/*` have no router-level guard requiring a WABA or agent to exist first. Iris does compute a `needsSetup` flag in-page, which is good defensive UX, but it's inconsistent — other Library pages apparently just render silent empty states (`wabas[0] ?? null` patterns). Founder's brief specifically asked whether "existing features are sequenced correctly along the natural user journey (e.g. can't configure a template before a WABA exists)" — answer: **no, sequencing is not enforced, only sometimes hinted at.** **RECOMMENDATION:** either (a) a shared "no WABA yet" empty-state component used consistently everywhere with a single CTA back to WABA connection, or (b) nav items themselves disabled/greyed until prerequisite exists (matches the existing "Human Handover: soon" pattern already in AppShell, so precedent exists in-house).

**F4. [HIGH] Agent creation has no WABA/phone precondition — agents can be created and left permanently phone-less.**
`CreateAgentPage.tsx`'s 5-step wizard does not check for or require a WABA before letting the user create an agent. `AgentsPage.tsx`'s own health logic explicitly treats "active with no phone" as a first-class expected state (`inactive`), confirming this dangling state is anticipated but not prevented at creation time. This is a "more managed, not more competent" outcome per the PM's Three-Question Filter — the user does work (5-step wizard) that produces a non-functional agent, discovering the missing phone only later on a separate page. **RECOMMENDATION:** the wizard should either require an existing WABA/phone at step 1, or end with an explicit "connect a phone number now" forced sub-step, not a silent gap discovered on a different page.

**U1. [CRITICAL] `bg-primary` / `text-primary` / `border-primary` / `focus-visible:ring-primary` render the OLD, pre-rewrite navy hex (`#160E7A`) as content-area color and focus ring, system-wide.**
`frontend/src/index.css:15` defines `--primary: 244 80% 27%` = `#160E7A` — the exact hex DESIGN.md's own changelog (2026-08-06) says it replaced with Karix Blue Zodiac `#11225F`. `--primary` was never migrated or removed. It is then used as the general "brand emphasis" color inside content surfaces on nearly every page: `CreateAgentPage.tsx` (step-rail active state, channel picker, every text-input focus ring, tone chips, "Generate with AI" button), `AgentsPage.tsx` and `DashboardPage.tsx` (icon chips), `SettingsPage.tsx` (icon chips), `LoginPage.tsx` (input focus ring, tab active state), `WabaDetailPage.tsx`. Two DESIGN.md rules broken at once: (a) "brand-navy on a card/table row/modal = REJECT" — every instance above is inside a content card, table cell, or form field, never chrome; (b) the mandated focus ring is `focus-visible:ring-brand-purple/40 ... ring-offset-background`, not navy/`primary`. This is the majority pattern used for brand emphasis throughout the app — nearly every form field, active-state chip, and icon accent is wearing a color DESIGN.md explicitly retired. Per persona-ux Step 1 (Token Grep) and Step 5 (Focus Ring Check), this alone would REJECT almost every screen.

**U2. [HIGH] Dense multi-column tables (6–8 columns) have zero mobile treatment — only `overflow-x-auto`, no responsive card/list fallback.**
`DashboardPage.tsx`'s `PhoneNumbersTable` (6 columns), `AgentsPage.tsx`'s main table (8 columns incl. Health/Status/Actions), and `WabaDetailPage.tsx`'s phone table (3 columns) each wrap a `<table>` in `overflow-x-auto` and stop there — no `md:` breakpoint that swaps to a stacked-card layout, no mobile base style at all. At the mandated 375px baseline this forces horizontal scrolling to read a row. DESIGN.md §0.1 requires "single column, no horizontal scroll" and lists "Multi-column at 375px, overflow-x" explicitly under what gets REJECTED. This is the most common mobile violation found and hits the three most-used data screens in the product.

**U3. [HIGH] Loading state on `WabaDetailPage` and `TemplateStudioPage` is a bare centered spinner + text, not a layout-matching skeleton.**
`WabaDetailPage.tsx:61-65` renders `<Loader2 className="animate-spin" /> Loading…` with no skeleton. `TemplateStudioPage.tsx:36-38` renders a single bare spinner with no page chrome at all. DESIGN.md's State Completeness rule and persona-ux Step 3 are explicit and literal here: "Skeleton matching final layout. Not a spinner in the center of a blank page" is the documented anti-pattern, matched exactly. By contrast `DashboardPage.tsx`/`AgentsPage.tsx` do this correctly (`AttentionSkeleton`, `MetricsSkeleton`, `AgentTableSkeleton` mirror final layout) — the inconsistency itself breaks "every screen that ships looks like it was built by the same team, on the same day."

**U4. [MEDIUM] Shadow token name drift: `shadow-surface-resting` used everywhere instead of the documented `shadow-resting`.**
DESIGN.md §2 names the elevation token `shadow-resting` (plus `shadow-lifted`, `shadow-none`) as the only permitted classes. Every page instead uses a custom class `shadow-surface-resting`, separately defined in `index.css:90-93` with presumably matching values. Functionally harmless — it's a real defined utility, not a raw Tailwind `shadow-md` — but it's a second, undocumented name for the same concept, exactly the drift DESIGN.md's "tokens are the ONE place" principle exists to prevent, and it means a literal grep for the documented token name (persona-ux's own methodology) would miss every card in the app.

**U5. [MEDIUM] `InboxPage.tsx`: hardcoded `bg-white`, no `h-dvh` anchoring, and a fixed two-panel layout with no mobile/off-canvas behavior.**
Uses `bg-white` directly (list panel, thread header, message bubbles) instead of `bg-card`/semantic tokens — light-mode-only color that will visibly break in dark mode, where `card` is `#161B22`, not white. The conversation-list (`w-80 shrink-0`) + thread-view split has no responsive collapse: at 375px both panels compete for space with no drawer or single-column stacking, unlike AppShell's own sidebar, which correctly implements an off-canvas mobile drawer. The page also escapes the shared layout via `-m-6` rather than a `h-dvh`-based approach, a hand-rolled deviation from the shared shell pattern.

### Findings

**F17. [HIGH] 14 entities use the TSID generator but are missing `@JsonSerialize(using = ToStringSerializer.class)` on their `@Id` field — their ids will silently lose precision in JS once a real TSID exceeds `Number.MAX_SAFE_INTEGER`.**
Confirmed by cross-referencing every entity carrying `@GenericGenerator(name = "tsid", type = TsidGenerator.class)` against which ones also carry the `ToStringSerializer` annotation the codebase itself already uses correctly on `Agent`, `Conversation`, `Message`, `Skill`, `Client`, `IrisSession`, `PhoneNumberSnapshot`, `ApiCallLog`, etc. (each of those has the matching "TSIDs overflow JS Number.MAX_SAFE_INTEGER" comment). These 14 do **not**: `domain/analytics/entity/AgentPerformanceHourly.java:18-21`, `ConversationSession.java:18-21`, `WebhookEvent.java:18-21`, `domain/client/entity/ClientAuditLog.java:23-26`, `ClientStaff.java:22-25`, `domain/templatestudio/iris/AiProviderCredential.java:25-28`, `IrisMessage.java:20-23`, `domain/user/entity/AccountModule.java:31-34`, `BusinessAccount.java:18-21`, **`User.java:18-21`**, `domain/waba/entity/KarixEsmeCredential.java:29-32`, `PhoneEsmeMapping.java:26-29`, `Waba.java:20-23`, `WabaAccountAccess.java:26-29`, `domain/webhook/entity/WebhookRaw.java:20-23`. `User.id` is the highest-impact one: `frontend/src/store/authStore.ts:5` declares `id: number` for the persisted auth user, so if `User.id` is ever serialized directly (not routed through a DTO that re-stringifies it) a large TSID will corrupt on the client. **Violates:** CLAUDE.md's explicit EL checklist item on TSID serialization; the codebase's own established, working pattern (14 other entities do this correctly with an identical comment, so this isn't a missing convention, it's inconsistent application of an existing one). **Not yet confirmed:** whether every controller path exposing these entities serializes the raw entity or always maps through a DTO first (would mask the bug in practice) — flagged, not verified, in the time available; worth a targeted grep of controllers returning these 14 types directly before treating this as low-risk.

**F18. [MEDIUM] `ConversationStore`'s four write methods accept an `accountId` parameter but never use it to scope the `findById` lookup — tenant isolation for this table relies entirely on callers passing an already-trusted `conversationId`, with no defense-in-depth at this layer.**
`domain/conversation/service/ConversationStore.java:44,70,100` (`saveInbound`, `saveOutbound`, `markNeedsHuman`) each do `conversationRepository.findById(conversationId).ifPresent(c -> {...})` — `accountId` is a method parameter but is never compared against `c.getAccountId()`. Today this is safe in practice because every caller resolves `conversationId` via `conversationStore.findOrCreate(accountId, ...)` first (an account-scoped call), so cross-tenant access isn't currently reachable — but the guard living implicitly in caller discipline, not in the method that owns the write, is exactly the pattern CLAUDE.md's checklist flags ("naked findById without tenant/access guard"). One new caller passing an untrusted `conversationId` (e.g. from a future API endpoint) would silently mutate another account's conversation with no compile-time or runtime signal. **RECOMMENDATION:** change these three lookups to `conversationRepository.findByIdAndAccountId(conversationId, accountId)` (mirroring the pattern already used correctly elsewhere, e.g. `AgentSkill.findByIdAndAgentId` in `SkillLibraryService.java`) — low-risk, contained change.

**F19. [LOW] Single `as any` cast found in the frontend, in `AgentDetailPage.tsx:2156`** — `api.get(`/agents/${agentId}/settings`).then((r) => r.data.data as any[])`. CLAUDE.md bans `any` outright ("Use any in TypeScript" is listed under Never). This is the only occurrence in the entire `frontend/src` tree (confirmed by grep — 1 file, 1 line), so the ban is respected everywhere else; this is an isolated miss, not a pattern. **RECOMMENDATION:** type the settings response properly (should be a small, known shape) — Fast Track eligible (1 line, 1 file).

**F20. [MEDIUM] The 401 interceptor redirects to `/login` but never clears the persisted Zustand auth store — `localStorage`'s `auth` key still reports `isAuthenticated: true` with a stale user after a session-expiry redirect.**
`frontend/src/lib/api.ts:9-18` — on any `401`, the interceptor only does `window.location.href = '/login'`; it never imports or calls `useAuthStore.getState().clearAuth()` (`frontend/src/store/authStore.ts:24`). Because the store is `persist`-backed to `localStorage` (`authStore.ts:26`, key `'auth'`) and a hard navigation doesn't itself clear it, the stale `isAuthenticated: true` + stale `user` survive in `localStorage` past the point the session actually died server-side, until the user explicitly logs out again (whatever calls `clearAuth()` — not found in the files read for this pass, likely a logout button handler elsewhere). Any component that trusts `useAuthStore().isAuthenticated` before the next authenticated API round-trip re-triggers a 401 (e.g. a route guard checking the store synchronously on mount) would render as if the user is still logged in. **Violates:** no explicit CLAUDE.md line, but is exactly the "auth store clearing vs redirect race" the task brief asked to check for, and is a real correctness gap, not speculative — the interceptor code has zero reference to the auth store. **RECOMMENDATION:** call `clearAuth()` synchronously before the redirect in the interceptor.

**F28.
