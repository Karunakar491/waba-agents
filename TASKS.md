### 16. bindPhone's onboarding gate is per-Agent-row, not per-phone — rebind to a different number reuses the wrong agent_id
- **Status**: Not started. EM-flagged 2026-09-03 during review of the agent_onboarding root-cause fix (see item below, and `AgentService.java`'s `bindPhone()`).
- **Why**: The new onboarding-before-settings fix gates on `agent.getMetaAgentId() == null`. If an agent that's already bound to phone A (and so already has `metaAgentId` set) gets rebound to a *different* phone B — nothing in `bindPhone()` or the controller blocks this (`ConnectPhoneModal.tsx`'s own comment: "Soft-warn, never a hard block") — onboarding is skipped, and the settings call for phone B gets scoped via `MetaApiClient.scopedPath()` using phone A's `agent_id`. Untested whether Meta's `agent_onboarding` endpoint is itself idempotent/safe to call again on an already-provisioned phone, so this isn't a trivial "just always call onboarding" fix. Currently only logs a `WARN` (`AgentService.java`, right before the onboarding gate) rather than blocking — never fails silently, but doesn't prevent the mis-scoped call either.
- **Plan**: (1) live-test what `POST agent_onboarding` actually does when called against a phone number that already has a live Meta-side agent (safe no-op returning the existing id? error? second entity?) before deciding the fix shape; (2) likely fix: gate onboarding on "does the *target phone number* already have an agent" (re-verify against phone B specifically) rather than "does this Agent row have any `metaAgentId` at all," or require an explicit unbind (clearing both `phoneNumberId` and `metaAgentId` together, matching `deleteFromMeta()`'s existing pattern) before allowing a rebind to a new number. See `backend/src/test/java/.../AgentServiceBindPhoneOnboardingTest.java`'s `rebinding_to_a_different_phone_currently_reuses_the_old_agent_id_without_reonboarding` test, which documents the current (not-yet-fixed) behavior on purpose.

### 14. Excel-upload UX has no row preview before sending to Iris
- **Status**: Not started. Found 2026-08-19 auditing the sheet-upload feature shipped the same day.
- **Why**: After a successful upload, the composer only shows an aggregate chip — `📄 filename (N rows)` — with zero visibility into the actual parsed column headers/values. The full parsed row data IS sent (as an invisible JSON blob embedded in the outgoing message text), but the user never sees it themselves before Iris starts acting on it. If a column got misread or the wrong sheet was picked, there's no way to catch it before the conversation is already underway. There's also no per-row progress once Iris starts working through rows (pending/drafted/confirmed/skipped) — it's one undifferentiated chat exchange regardless of row count, and no way to exclude specific rows before sending (all-or-nothing).
- **Plan**: needs its own scoping — a real preview component (expandable table of parsed rows/columns) shown immediately on upload success, a visible truncation banner (not buried in a chip parenthetical) when `truncated: true`, per-row status tracking as Iris works through them, row-exclusion before send, and a default "Create templates from this sheet" action button instead of requiring the user to type something. Real UX/product design work — new preview component + row-selection state + cross-turn progress tracking — not a quick patch. Full frontend gate sequence applies.
